# 调用链分析（Call Chain Analysis）

目标：获取 **入口 → 处理逻辑 → 敏感操作** 的完整调用链，并识别、评估其中的阻断条件（校验点），判断能否绕过。

两条分析思路（污点追踪 + 逆向技巧）服务于同一目的，可交替使用。

## 读法提示：超大反编译体的分段提取

业务分发函数（解析 key=value、多分支命令构造）反编译输出常达几十 KB 且为单行 JSON，直接整段读会挤爆上下文。处理方式：

1. **不要一次通读**：先 `decompile_function` 保留输出文件，用 `python3` 提取（`json.load` 后按 `execv|popen|--command=` 等关键词找偏移，再按区间切片打印）
2. **按序号驱动**：先定位 sink 调用点与拼接点（`append` 前缀常量、`execv` 参数、`fork`/`dup2`），再向前回退几百字符看分支条件（`rfind(key,0)==0` 之类前缀判断），最后回看入口传参
3. DAT 常量（`DAT_xxx`/字符串拼接片段）用 `inspect_memory_content` 直接读字节确认内容，不要靠猜

## 一、污点分析思路

### 三要素

| 要素 | 含义 | 本场景对应 |
|------|------|-----------|
| **source（污点源）** | 不可信输入入口 | 入口函数参数、socket 接收缓冲区、配置文件内容 |
| **sink（污点汇聚点）** | 污点流入的危险操作 | 命令执行、路径操作、内存拷贝、权限判断 |
| **传播路径** | source → sink 的数据流 | 参数从入口到危险函数的调用链 |

### 主线：入口向下追踪（主要工作）

从已识别的入口处理函数出发，沿数据流观察参数去向：

1. `decompile_function(入口函数)` → 看参数如何被使用、传给谁
2. 遇到子调用 → `get_function_callees` / `decompile_function(被调用者)` 跟进
3. 用 `analyze_dataflow(地址, 参数, direction="forward")` 做 PCode 值传播追踪
4. 沿途记录：数据是否被校验、是否被截断/转换、是否跨信任边界

在每个处理步骤验证三件事：**数据还可达吗？还可控吗？校验够吗？**

### 可选：sink 反向回溯

仅当**危险函数族数量很少**时值得反向枚举（如命令执行族 exec*/system/popen，全程序通常仅数个调用点）：

1. `list_imports` 过滤命令执行类函数
2. `get_xrefs_to(危险函数地址)` → 找到所有调用点
3. 反编译调用点 → 向上追溯危险参数来源
4. 与入口向下的路径**交汇处** = 疑似漏洞点

> 注意：memcpy/strcpy 这类高频函数调用点可能上百，不适合反向枚举，应依赖入口向下的污点追踪发现。

## 二、逆向技巧集

### libc 函数逆向

需要确认危险函数的真实行为时，可逆向 libc.so 中的实现：

- 场景：确认 `popen`/`execvp` 的真实调用约定、`getaddrinfo` 的输入要求、格式化函数的确切处理
- 方法：用 IDA/Ghidra 打开 `libc.so.6`，`search_strings` + xref 定位函数实现，确认它如何解释参数
- 价值：判断"这个危险函数到底会不会把参数当命令/路径执行"，避免误报或漏报

### 导入表定位

- `list_imports` 一次拉全量，**本地过滤**比多次 glob 查询快
- 过滤标准库符号（`_ZN*`/`_ZSt*`/`__cxa*` C++ 运行时）后，剩余才是值得关注的
- 导入表快速判断：程序用了哪些库（glib/Qt/libcrypto）、具备哪些能力

### 间接调用的追踪（caller 空时）

D-Bus/GObject 程序普遍把业务 handler 挂为异步回调，`get_function_callers` 常返回空。处理流程：

1. `get_xrefs_to(候选函数)` → 区分引用类型：`INDIRECTION`/`DATA` 引用来自 vtable、信号注册表、编译期常量表
2. 反编译持有 DATA 引用的函数 → 找 `g_signal_connect_data` / `g_task_new` + `g_task_run_in_thread` 注册点（GTask 线程回调是 GDBus 服务的常见形态）
3. 同时核对与注册点相邻的 `"<方法名>"` 字符串（如 `handle-run`），即可确定 handler 与 D-Bus 方法的对应关系
4. 数据流分析只认 code 引用，INDIRECTION/DATA 引用是**找注册点专用**——不要因为"无 caller"误判为死代码

### 交叉引用类型区分

- `get_xrefs_to` 结果区分 **code 引用**（真正的调用/访问）与 **data 引用**（vtable、字符串表、全局结构）
- 追踪数据流只关注 code 引用；data 引用用于发现结构体/回调表

### 字符串锚点

- 报错信息、路径、格式串、接口名作为锚点
- 搜到字符串 → xref → 反推业务逻辑
- 适用于定位硬编码路径、配置项、日志分支

### 常量模式

- 魔数、权限位（`0o777`）、命令号、长度上限常量
- `search_instructions` / `list_globals` 搜索 → 找到关键判断点
- 帮助识别"这里有个边界检查"或"这里直接用了用户值"

### 函数指针表推断（符号缺失时）

- 结构体中的函数指针数组（vtable 风格）→ 回调入口
- 从注册函数（`register_*`/`g_signal_connect`）的 xref 反向找表
- 适用于 stripped 二进制，推断分发逻辑

## 三、阻断条件分析（校验点评估）

调用链上的每个校验点都要评估可绕过性：

| 检查项 | 评估方法 |
|--------|---------|
| 校验存在性 | 该路径上有没有长度/范围/权限检查 |
| 校验完整性 | 检查和使用是否在**同一锁/同一时刻**下 |
| 校验一致性 | 检查的变量是否在使用前被重新赋值/截断 |
| 类型边界 | 32 位兼容路径是否和 64 位一致 |
| 权限模型 | 检查的是 `capable` 还是 `ns_capable`；检查 A 对象却操作 B 对象 |

**记录调用链格式**：`入口 → 校验点 → 处理逻辑 → 敏感操作`，标注每个校验点"是否可绕过、如何绕过"。
