# 用户态漏洞模式（Vuln Patterns）

对疑点位置，对照以下漏洞模式验证三件事：**可达性、可控性、校验缺失**。每条模式说明其污点要素（source/sink）与检查项。

不要因为代码中出现 `system`、`memcpy`、`parse` 等关键词就报告漏洞——必须证明三件事全部成立。

## 1. 命令注入

- **source**：入口字符串参数（D-Bus 方法参数、socket 消息、配置值）
- **sink**：`system` / `popen` / `exec*` 族
- **检查项**：
  - 参数是否拼入命令字符串（`"kaiming run --command=" + 参数`）
  - 是否经过转义/白名单（可绕过：`;`、`|`、`$()`、换行）
  - 调用前是否有权限/namespace 校验（可达性）
- **易发场景**：D-Bus 方法带 command/路径参数；守护进程执行外部命令

## 2. 路径处理（穿越 / 符号链接）

- **source**：入口路径参数、配置中的路径
- **sink**：`open` / `rename` / `unlink` / 文件操作
- **检查项**：
  - 路径是否拼接用户输入（`/opt/xxx/` + 参数）
  - 是否校验 `..`、绝对路径、符号链接
  - TOCTOU：检查路径后、使用前路径是否可被替换
- **易发场景**：文件路径参数、临时文件处理、配置加载

## 3. 解析类溢出

- **source**：消息头、配置项、用户提供的长度字段
- **sink**：`memcpy` / 堆/栈分配 + 拷贝
- **检查项**：
  - 长度字段是否与实际拷贝大小一致
  - `len + header_size` 是否可能整数溢出
  - 数组索引是否越界（index 来自用户）
  - 类型混淆：把一种结构当作另一种解析
- **易发场景**：socket 消息头解析、配置解析、嵌套属性解析（netlink 属性）

## 4. 整数处理（溢出 / 符号 / 截断）

- **source**：用户提供的数值（长度、count、offset、index）
- **sink**：分配、拷贝、数组访问、循环边界
- **检查项**：
  - 乘法/加法是否溢出（是否用 `array_size`/`struct_size`）
  - 负数是否绕过范围检查（有符号比较）
  - 检查后的值是否被重新赋值/截断（32/64 位）
  - 分配大小 vs 实际使用大小是否一致
- **易发场景**：长度计算、数组分配、偏移计算

## 5. 校验 / 权限绕过

- **source**：入口调用者身份、请求参数
- **sink**：权限判断点、敏感操作
- **检查项**：
  - 权限检查是否存在于所有分发路径（有的 command 漏检）
  - 检查与使用是否一致（检查 A 操作 B）
  - 检查的是当前 namespace 还是 init namespace
  - 校验后可被重新赋值的变量是否仍按原值使用
- **易发场景**：ioctl command 分发、D-Bus 方法权限、配置白名单

## 三问题检查汇总

对每个候选漏洞，必须能回答：

| 问题 | 确认内容 | 证据 |
|------|---------|------|
| 可达性 | 攻击者能否到达该路径 | 入口暴露面、权限要求、是否需要设备/配置 |
| 可控性 | 攻击者能否控制关键数据 | 输入来源、格式、未校验程度 |
| 校验缺失 | 是否在错误信任边界使用数据 | 缺失/错误/不一致的检查 |

**证据不足时**：归类为"审计线索"，写清已确认事实、尚未确认、下一步应查看，不要直接报漏洞。
